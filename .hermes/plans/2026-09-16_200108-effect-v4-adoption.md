# Mieux exploiter Effect v4 — Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task, uniquement après autorisation explicite. Ce document est une réflexion, pas une demande d’exécution.
>
> **Exploration approfondie et revue disponible :** [plan revu des tâches 1, 2, 3, 4 et 6](./2026-09-16_204821-effect-v4-exploration-reviewed.md). Il prévaut sur les hypothèses correspondantes ci-dessous, notamment sur le bridge transactionnel, le GC et l’adoption d’Effect côté média. Sa numérotation suit le message : T2 = DB/R2, T3 = frontières serveur, T6 = média.

**Goal:** Renforcer les garanties d’erreur, de concurrence et de cycle de vie sans réécrire ViteSakuga autour d’Effect.

**Architecture:** TanStack conserve routing, rendu, transport et état serveur client; Better Auth conserve l’authentification; XState conserve les transitions de conversion. Effect porte les programmes métier et les adaptateurs I/O, avec des frontières Promise explicites. Kysely et Drizzle restent en place tant qu’un remplacement ne démontre pas un gain net.

**Tech Stack:** Effect installé `4.0.0-rc.112`, React/TanStack Start, Kysely/Drizzle, Neon HTTP + transactions WebSocket sur Workers, PostgreSQL local, PGlite/RustFS pour les tests, Vitest 5.

## Diagnostic

Lecture du dépôt au commit `9308020`, des docs v4 et des déclarations des paquets installés. Aucun test, build ou déploiement exécuté : les conséquences de concurrence et les gains de performance ci-dessous restent à reproduire/mesurer.

**Déjà acquis — ne pas refaire :** services `Context.Service`, composition `Layer`, méthodes `Effect.fn`, erreurs `Schema.TaggedError`, validation Effect Schema/Standard Schema, configuration `Config`/`Redacted`, horloge virtuelle pour points et rate limit, instrumentation SQL. Exemples : `src/lib/comments/comments.service.ts:52`, `src/lib/env/defs.ts:65`, `src/lib/effect/schema.utils.ts:96`, `src/lib/points/points.service.test.ts:183`.

Le manque principal n’est pas le nombre de modules Effect employés : plusieurs frontières natives empêchent encore de bénéficier de ses garanties de bout en bout.

## Plan priorisé

### 1. Priorité haute — fiabiliser la transaction Effect/Kysely

**Constat :** `src/lib/effect/effect.utils.ts:42-46` ne propage pas les besoins `R` et ne déclare pas les erreurs propres au démarrage/commit. À `:88-95`, un `Effect.runPromise` interne repart sans contexte ni signal du parent; tout rejet est casté en `E`, y compris une erreur du driver ou un défaut.

**Approche :** conserver Kysely; rendre le bridge honnête sur `A/E/R`, préserver services/horloge/traces, distinguer échec métier, défaut et interruption. Relier annulation et terminaison de transaction; transmettre un signal seul ne suffit pas à prouver que rollback et libération sont terminés. Vérifier aussi l’annulation réellement supportée par les drivers.

**Fichiers :** `src/lib/effect/effect.utils.ts`, `src/lib/effect/effect.utils.test.ts`, `src/lib/db/neon-transaction-dialect.ts`; signatures des services appelants si nécessaire.

**Premier lot :** écrire les tests de contexte/horloge puis d’interruption; constater leur échec; corriger le bridge; repasser ces tests et les mutations consommatrices.

**Acceptation :** service injecté et TestClock visibles dans la transaction; erreur métier conservée; BEGIN/COMMIT/ROLLBACK classifiés; rollback sur défaut/interruption; pas de commit tardif après une annulation acquittée. Vérifier séparément PGlite et la voie Workers/Neon.

### 2. Priorité haute — une frontière serveur cohérente, des durées de vie explicites

**Constats :** `createHandler` protège déjà les erreurs (`src/lib/server-fn.handler.ts:111-135`), mais `getUserSession` exécute directement son programme sans cette même protection (`src/lib/auth/auth.middleware.ts:7-21`). `makeDBLayer` inclut systématiquement stockage et tracing (`src/lib/db/layer-factories.server.ts:45-64`); le client S3 est construit dans cette layer (`src/lib/storage/storage.adapter.ts:50`).

**Approche :** factoriser l’exécution/sanitisation commune, garder les imports dynamiques serveur. Fournir DB, session et stockage seulement aux chemins qui en ont besoin. Définir les propriétaires des ressources et leurs finalizers avec `Scope`/`acquireRelease`; propager l’annulation depuis la frontière HTTP lorsque l’adaptateur TanStack/Nitro la rend disponible. Une annulation ne doit pas devenir une erreur métier ordinaire.

**Attention Workers :** pas de runtime global contenant headers, session ou WebSocket. Le dialecte Neon crée déjà une connexion par transaction pour respecter cette contrainte (`src/lib/db/neon-transaction-dialect.ts:50-58`). `ManagedRuntime` est un candidat pour les tests et le serveur Node, pas une recette universelle de cache serveur.

**Fichiers/tests :** handler et son test, `auth.middleware.ts`/`auth.middleware.test.ts`, `layer-factories.server.ts`, `storage.adapter.ts`, `db/test-utils.ts`. Ajouter des tests de non-fuite inter-requêtes et de fermeture exacte des ressources. Adapter la durée de vie du harness avant de rendre le stockage scoped : ne pas rendre un service déjà finalisé après `runPromise`.

### 3. Priorité haute — sécuriser les mutations DB + R2

**Constats :** upload possède déjà une compensation (`src/lib/posts/posts.service.ts:754-868`), mais les erreurs de nettoyage sont ignorées. Le remplacement promeut le fichier, archive puis modifie le post sans transaction DB commune (`src/lib/videos/videos.service.ts:300-319`). La restauration et le GC ont également des fenêtres de concurrence (`:395-415`, `:440-499`).

**Approche :** un programme métier explicite : vérifier → préparer l’objet → mutation DB atomique → confirmer. Compensation idempotente, attachée aux sorties pertinentes avec `onExit`/`onError`, observable lorsqu’elle échoue. Ne pas supprimer un objet durable sur une sortie réussie, ni sur un résultat de commit incertain sans réconciliation. Coordonner remplacement/restauration/GC : une simple relecture avant DELETE ne ferme pas une race.

**Limite :** Effect n’offre pas une transaction distribuée entre PostgreSQL et R2. Garder le lifecycle du staging et le GC; un crash Worker peut empêcher un finalizer de s’exécuter. Décider d’une intention persistée/outbox seulement si une reprise automatique durable est requise.

**Fichiers/tests :** `posts/posts.service.ts`/`posts.fn.test.ts`, `videos/videos.service.ts`/`videos.service.test.ts`, `storage/storage.adapter.ts`/`storage.test.ts`.

**Acceptation :** échecs avant/après promotion, rollback DB, compensation en échec, deux remplacements concurrents, restauration pendant GC. Aucune relance automatique globale d’une mutation non idempotente.

### 4. Gain rapide — généraliser les patterns Schema et Clock déjà présents

**Constats :** les recherches utilisent `Effect.try(() => parse(...))` (`src/lib/posts/posts.service.ts:433`), mais certains décodages du détail restent synchrones dans le programme (`:637`, `:656`). L’ancienneté des promotions lit `Date.now()` (`src/lib/promotions/promotions.service.ts:98-101`); les filtres posts aussi (`src/lib/posts/posts.service.ts:88-105`).

**Approche :** `Schema.decodeUnknownEffect` + mapping vers `RowParseError` dans les programmes; garder les validateurs synchrones/Standard Schema aux frontières adaptées. Capturer une seule valeur `Clock.currentTimeMillis` par décision métier; transmettre `now` aux fonctions pures. Ne pas réécrire le calcul de jour local déjà basé sur DateTime.

**Tests :** lignes DB malformées distinguées des entrées utilisateur; seuils exacts promotion/today/week/month. Cibles : `posts/posts.fn.test.ts`, `promotions/promotions.service.test.ts`, `effect/schema.utils.test.ts`.

**Compatibilité vérifiée :** `@effect/vitest@4.0.0-rc.112` exige Vitest `>=4.1.0 <5.0.0`, contrairement au Vitest 5 du projet. Ne pas l’installer de force ni rétrograder Browser Mode; utiliser `effect/testing/TestClock`, déjà opérationnel. `effect/testing/FastCheck` et `Schema.toArbitrary` sont disponibles pour des propriétés utiles, sans imposer un nouveau runner.

### 5. Performance — regrouper avant de paralléliser

**Constats :** `PostEditsService.listForPost` charge les approbations une édition à la fois (`src/lib/post-edits/post-edits.service.ts:506-508`). La queue de promotion effectue des lectures d’activité par candidat (`src/lib/promotions/promotions.service.ts:188-206`). Les compteurs de profil utilisent `Effect.all` sans option (`src/lib/users/users.service.ts:379-432`).

**Approche :** requêtes SQL groupées en premier; `Effect.all`/`forEach` avec concurrence bornée uniquement pour les I/O restantes réellement indépendantes. Leur comportement par défaut est séquentiel, pas parallèle. Ne pas paralléliser aveuglément une transaction sur une seule connexion.

**Acceptation :** même résultat et même ordre; nombre de requêtes maîtrisé, plafond de concurrence vérifié, mesure de latence sur scénario reproductible. Tests existants : `post-edits/post-edits.service.test.ts`, `promotions/promotions.service.test.ts`, `users/users.fn.test.ts`. `RequestResolver` ou `Stream` seulement si un besoin de batching inter-appels ou de traitement paginé volumineux subsiste.

### 6. Observabilité — rendre visibles les garanties précédentes

**Constat :** spans SQL et `Effect.fn` existent; `TracingLive` active un `NodeSdk` conditionnel (`src/lib/effect/tracing.ts:17-25`). Pas de métriques applicatives trouvées dans les services inspectés; réception effective des traces non vérifiée.

**Approche :** span racine du cas d’usage, `debugId` corrélé à tous les logs, métriques de latence/échec/interruption et de compensation échouée. Pas d’identifiants utilisateur en labels de métriques, pas de secrets ou URLs présignées en attributs. Comparer le SDK actuel aux exporters HTTP `effect/unstable/observability/Otlp` sur Workers; `Otlp.layerJson` existe dans le paquet installé, mais reste une API unstable.

**Acceptation :** une vraie trace reçue par un collecteur, SQL rattaché à son parent, compteur observable, flush borné compatible avec la fin de requête. Collecteur indisponible ≠ échec de l’action métier. Ne pas simplement ajouter des compteurs sans export ni alerte exploitable.

### 7. Frontend ciblé — un traitement média annulable, pas un nouveau framework client

**Constats :** sélections successives non protégées contre des résultats obsolètes (`src/lib/upload/useVideoProcessing.ts:113-166`); `Input` sans `dispose` dans la génération de vignettes (`src/lib/upload/upload.processor.ts:77-167`); PUT sans signal (`src/lib/upload/useUploadForm.ts:307-311`). L’acteur de conversion libère déjà son Input dans `finally`, mais retourne un cleanup vide (`src/routes/-convert.machine.ts:467-472`).

**Approche :** un scope par traitement média; arrêt de l’ancien traitement lors d’une nouvelle sélection/d’un unmount. Brancher concrètement les finalizers sur `Input.dispose()`, `Conversion.cancel()` — API vérifiée dans mediabunny installé —, `fetch` et les blob URLs. Conserver les URLs affichées jusqu’à leur remplacement, pas seulement jusqu’à la fin du calcul. Garder les événements et états XState; un arrêt volontaire n’est pas un toast d’échec.

**Tests :** A sélectionné puis B rapidement, démontage pendant analyse/PUT/conversion, aucun résultat tardif, fermeture des ressources sans invalider l’aperçu courant. Cibles : `upload/upload.processor.test.ts`, `upload/useUploadForm.test.ts`, `src/routes/-convert.machine.test.ts`, `e2e/upload.spec.ts`, `e2e/convert.spec.ts`; nouveau test Browser Mode du hook si nécessaire.

## Ce que je ne changerais pas maintenant

- **TanStack Query/DB/Form/Router, Better Auth, XState :** pas de migration Atom, HttpApi ou RPC pour utiliser davantage de packages. Préserver rendu, hydratation, navigation et upload direct vers R2.
- **Kysely/Drizzle :** ne pas migrer vers `@effect/sql-pg` par principe. Il utilise `pg`, pas le même chemin que Neon HTTP/WS sur Workers. Étudier `SqlClient.withTransaction` seulement si fiabiliser le bridge devient plus complexe qu’un adaptateur natif démontré sur les cibles réelles.
- **Configuration et tooling :** `Config`, `Redacted`, `@effect/tsgo` et presets Oxlint sont déjà là (`package.json:45`, `.oxlintrc.json:2-5`). Resserrer les garde-fous ciblés plutôt qu’ajouter des dépendances ou bannir tout `async` légitime. Les tests sont actuellement ignorés par Oxlint (`.oxlintrc.json:32-33`) : activer leur lint progressivement, pas en chantier parallèle massif.
- **Workflow/Cluster/queues durables :** seulement avec un besoin de jobs survivant aux requêtes. Pas pour du CRUD ordinaire.
- **Retries/cache :** retry uniquement les erreurs transitoires d’opérations idempotentes, avec budget et backoff; tenir compte des retries AWS SDK. Aucun cache global de session, aucun cache Effect présenté comme partagé entre isolates.

## Vérification future et ordre de livraison

Ordre conseillé : **bridge transactionnel → frontière serveur → mutations stockage → Schema/Clock → mesures performance/observabilité → pilote média**. Schema/Clock peut avancer indépendamment; l’instrumentation de base accompagne les premiers lots.

Pour chaque lot : test comportemental rouge → changement minimal → test vert → vérification des consommateurs. Première commande ciblée : `nub exec vitest run src/lib/effect/effect.utils.test.ts`.

Garde-fous après implémentation : `nub exec tsc --noEmit`, `nub run lint:check`, `nub run format:check`, `nub exec vitest run --maxWorkers=1`; puis `nub run test:browser` pour le client, `nub run build`, `nub scripts/check-prod-build.mjs`. Pour média : `nub exec playwright test --config=e2e/playwright.config.ts e2e/upload.spec.ts e2e/convert.spec.ts`. PGlite ne prouve pas les races PostgreSQL ni les restrictions I/O Workers : prévoir des sondes isolées sur ces cibles, jamais sur des données partagées.

Synchroniser `docs/server-functions-api.md`, `docs/database-conventions.md`, `docs/testing.md`, `CONTEXT.md`; `docs/features.md` si les garanties ou interactions visibles changent. Aucun commit/push automatique, aucune réécriture incidente des migrations.
